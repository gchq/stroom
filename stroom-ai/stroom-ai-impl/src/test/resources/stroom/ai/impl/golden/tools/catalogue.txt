## activity_timeline

isReadOnly: true
readsUntrustedContent: true
boundsItsOutput: true
strict: null
metadata: { }
offered in modes: 

### Description

Builds one user's (or entity's) activity timeline for a period from any Elastic Index sources, in code. Two levels: detail spans (focus sessions where a source records window focus; pairs from a start to its end, e.g. a process's start and end, the schema's, a skill's, or inferred from the user's own events; spans bounded by a key, e.g. a session id; activity periods, the actions in neither close in time, by host or source) and activities rolled up from them (what the user was working on). Events without roles are classified from their Events XML (the EventDetail element and Action), else the index's fields; the user and time always come from the index. Each index's user field: userField, the AGENTS doc's ## Fields, a field convention, the index's documentation, else asked. Data-quality flags for missing events. Omit sources to ask the user which (or read all you can use). includeTargets adds what was done to the person, apart from their activity. Its tables draw as timelines with gantt_chart (dashboards group) as they are; the result gives the arguments for the view.

Counts and sums come straight from Elasticsearch and may include documents from streams the user can't see or that have been deleted, so they can differ from Stroom searches (run_stroomql) and dashboards: when the user needs figures that match those exactly, use a Stroom search (run_stroomql). FIRST and LAST are reserved: name columns e.g. first_seen and last_seen. In RLIKE, @ matches any string: escape it, or use LIKE for simple patterns. ES|QL has no IF: use CASE(condition, then, else). Patterns: first seen, MIN(@timestamp) BY user, value; spraying or scans, COUNT_DISTINCT(target) BY source; an index's baseline vs recent, one STATS with COUNT(*) WHERE @timestamp < x per period; a cold-start guard, WHERE on a history count. The rows are written to a table in the workspace too, for the table tool.

## sequence_query

isReadOnly: true
readsUntrustedContent: true
boundsItsOutput: true
strict: null

offered in modes: 

### Description

Use for any 'X, then Y, by the same user/host, within N' question, in one data source or across several, rather than joining the results of separate queries (esql_query, search_events, run_stroomql) by hand. The engine follows the data sources: on Elastic Index docs on one cluster, one EQL sequence in Elasticsearch, with everything below; on any other (a Lucene index, a view), a StroomQL windowed join run in Stroom, which takes 2 steps joined by by (no until, missing or runs; no caseInsensitive, length, IS_NULL or regex; step 2 needs a condition) and refuses a first step with too many events; the result says which ran and why. On Elastic Indexes it runs instead as a streaming join in Stroom (engine=stream; chosen itself where EQL can't: a first step too big for EQL, different time fields, keysOnly or transform): each step read in join-key order and merged, no side capped, sizes estimated first; keysOnly=true for a step that only says which entities count (e.g. a team's users in a directory), transform for join values sources write differently (CORP\jsmith vs jsmith); a join that finds nothing says why. Finds ordered sequences of events: e.g. a USB device plugged in then a file copied to it; a clipboard copy then PowerShell within 2 minutes by the same user on the same host; 20 failed logons then a success. Give steps (2 or more, in order), each with its doc, its where conditions (all must hold; NOT_IN for none of a list; length=true to compare a string's length), any_of (optional, at least one must hold), its own join fields (by, same number and order in every step: the same entity in each doc's own names), missing=true for 'and then NOT ...', runs=N for N in a row; until for a step that ends a sequence. maxspan: how far apart the first and last events may be, from the user's words ('within 2 minutes' is 2m), at most 24h; if they didn't say, leave it out and the user is asked. Fields are checked against each doc's (describe_data_source gives them). Each step is counted first: the result says when a later step is far more selective, and a first step too big for EQL runs as the streaming join (with engine=eql it is refused before it runs: narrow the window or the first step, or runAnyway=true). The result gives the EQL, a summary per entity, the sequences with each step's StreamId/EventId, and a validated StroomQL review query per doc, for a saved query (propose_query) or a dashboard with the event preview (propose_dashboard). Each reads one doc: when the hunt spans several, ask the user which doc to review (ask_user, the docs as options), then offer that doc's; on other data sources the windowed join itself is the review query. EQL sequences come straight from Elasticsearch, as ES|QL counts do, and may include streams the user can't see or deleted ones. Docs on different clusters and nested fields are refused. ## table

### Description

Queries a table in the workspace (an attached table in /attachments/, a tab's results that current_results saved in /tabs/results/, or a .csv or .tsv file) exactly, in code: eval adds columns worked out for each row, where filters rows, then groupBy and aggregates (or distinct, for each distinct value with its count) summarise them, orderBy sorts and limit cuts the result. Use mask with distinct or groupBy to count free text (e.g. messages) as patterns, with numbers, IPs, dates and IDs masked. Use this for any figures; never count rows or work figures out by reading them. Give join to match its rows with another table's first, e.g. on a user and an id, within some seconds. To join two Stroom data sources, a StroomQL join (run_stroomql) is better. Give out to write the result to a file.

Expressions (eval, and aggregates given as expression) are in Stroom's expression language, as in dashboards: ${column} is a column's value, 'text' or "text" a string, operators are + - * / % ^ and = != < <= > >=, and functions are called as name(arguments). The names are Stroom's, not SQL's: the mean is average(), not avg(). A cell that is a number is a number (except one with a leading zero, e.g. 007, which is text); others are text, which date functions read as dates. An empty cell is no value, and a failure (e.g. arithmetic on text) gives ERR: in its cell. In aggregates, min and max take an empty cell as the least value, so filter with not_empty first. For example: eval {"as": "rate", "expression": "round(${bytes} / ${seconds}, 1)"}, {"as": "site", "expression": "upperCase(substring(${host}, 0, 3))"}, {"as": "hour", "expression": "formatDate(floorHour(${time}), 'yyyy-MM-dd HH:00')"}; aggregates {"as": "error %", "expression": "round(sum(if(${status} = 'ERROR', 1, 0)) / count() * 100, 1)"}.

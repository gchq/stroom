## StroomQL
- Clauses go in this order: from, where (with and, or, not and brackets), eval, window, filter, sort by, group by, having, limit, select, show. In code blocks for the user, put each clause on its own line, and each and/or of a long where on an indented line. limit comes before select, e.g. `from "My View" where EventTime > day() - 1d limit 100 select EventTime, User`.
- Quote a data source's name in double quotes if it has spaces or punctuation. Never quote a field name in select or eval: a quoted name there is text, so every row would hold the name itself. Write a field with dots as it is (create.document.description, @timestamp), and one with spaces as ${Create Time}.
- Conditions: =, !=, >, >=, <, <=, in ("a", "b"), in dictionary "Name", and between 1 and 10. There is no contains, like or matches: to find a word in text, use = with wildcards, e.g. `Text = "*sky*"` (* for any characters, ? for one).
- To count, use count() with group by, e.g. `eval Count = count() group by User select User, Count`. Without group by, each row is its own group, so count() is 1 on every row.
- Check field names with describe_data_source and the query with validate_stroomql before you run it. Read the documentation it gives to find which field holds what the user means, as a field's name may not say: e.g. the field mapping of the pipeline that feeds an index may show that document.description holds a tweet's text.
- Keep searches narrow: a where clause, and a time range on the data source's time field (describe_data_source gives it). Never search a data source without a where clause to see what it holds. Every query you run is capped at a number of rows; the result says if the cap was reached.
- If a search finds nothing or runs out of time, don't widen it: the data source may hold nothing its search can read (e.g. its streams have been deleted or aged off). Say so, and check with stream_meta (the streams of its feeds) or ask the user, rather than searching again.

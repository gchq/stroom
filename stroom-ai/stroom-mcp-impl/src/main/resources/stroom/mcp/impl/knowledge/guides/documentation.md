# Pipeline documentation

Every pipeline built, changed or evaluated gets a Documentation doc with the pipeline's name, written with
`write_documentation` in Markdown. Its title (the `# ` line) is the doc's name, set by the tool: start with your first
section, and don't put a version in a heading of your own. The same content is returned in the chat. On an update, revise the sections
that changed; the tool keeps the `## Version control` block at the end, with an `Unreleased` row previewing the
build's changes until it is promoted (give `change`: what changed and why; a new
doc's is "Created"). Changes made while a build is worked on wait there, hidden, and become one row (version, date,
who, through which agent and model, what changed, the XSLT version) when the build is promoted. Each XSLT the
server saves keeps the same history in its own Documentation tab (a `## Version history` table, previewed the same
way), with edits made by hand found and recorded as such; the code itself is left as generated. Below the history,
hidden, is what the server keeps for the XSLT (its mapping, pending changes): a note there asks people to leave it.

## Sections

| Section | Events pipeline | Indexing pipeline |
| --- | --- | --- |
| Purpose and data | Feeds, source system, record format, volumes, the sample files used | Source feed, destination index, Elastic Cluster |
| Processing | Element chain, inherited template, reference data and dictionaries, decoration | Element chain, inherited template, enrichments |
| Field mapping | Generated by the tool (below) | Generated by the tool (below) |
| Output | Anything beyond the Field mapping's counts: volumes, Events streams produced | Index template name and version; verification searches and results |
| Conformance | Schema validation and quality pass rates | The verification searches |
| Errors | Generated by the tool (below) | Generated by the tool (below) |
| Open items | Suggestions and known limitations; input fields not mapped | Suggestions and known limitations |

## Field mapping: generated, never typed

`write_documentation` writes this section itself. It reads the mapping (or index plan) kept with the pipeline's
XSLT, which `build_translation_xslt` stores when it saves (`build=`, `name=`), or `save_xslt` when given
`index_plan=`, steps it over the
`stream_ids` you pass (the sample raw streams for an events pipeline, the Events streams for an indexing
pipeline), and puts the result in place of whatever the markdown has under `## Field mapping`. Up to 200 records
are stepped, spread evenly over the streams given, so pass all the sample streams: each adds the kinds it holds. So:

- Save every generated XSLT with its mapping (`build_translation_xslt build=... name=...`, or `save_xslt
  index_plan=...` for an indexing XSLT). Without it, an events pipeline's doc
  must bring its own `## Field mapping` section, and the tool refuses one that does not.
- Pass `stream_ids` to `write_documentation`, for every indexing pipeline and every events pipeline whose XSLT
  keeps a mapping: the tool refuses without them, as the section goes down to the field with the values the sample
  gave. An indexing XSLT written by hand keeps no plan: its section lists the fields of the documents it writes,
  how often and their values, but not where each comes from (save it with `index_plan=` for that). `build_translation_xslt` with `field_mapping=true`, `pipeline_uuid` and
  `stream_ids` returns the same section as a preview, by stepping the sample (slow): once, if at all, when the
  mapping is settled; never while fixing it.
- Change the mapping and regenerate rather than editing the XSLT: `build_status` reports an XSLT that is no
  longer what its mapping generates, and a documentation whose Field mapping predates the current mapping or
  XSLT (a digest marks the section).

### What the section holds (events pipelines)

How records are read, when it applies: `for_each` (one record, several events), the kinds left untranslated
(`drop_when`, with the reasons), and the fields `extract` parses out of text.

Then, laid out by event type (the default):

**Common fields**: a table of the `EventTime` and `EventSource` elements every rule writes from the same source,
with columns XPath, Description (what the field means for this source, as you described it: see below), From (the mapping: `` `badge_user` (lower)``, `` lookup `USER_DIRECTORY` by
`user` -> `name` ``, `` first of `time`, `timestamp` ``, `` `roles`, one per value ``, a constant in quotes, a value
map as `ok -> true, fail -> false`), and Sample values: the values the sample's events got, up to three, then how
many more; "(several per event)" for repeats; "(not in the sample)" when no sampled event got it. An element the
sample's events have that the mapping does not write (a hand edit, a later step) gets a row saying so.

**Event types**: a `#### <rule>` section per rule, with its conditions and how many of the sample's events it wrote
(exactly: the documentation run marks each Event with its rule), and a table with the same columns of its own
fields: `TypeId` and `Description` first, then its `EventDetail` elements and any `EventSource` element it writes
differently. Rules with roughly the same fields (logon and logoff, Send and Receive: three quarters of their fields
in common, an action element counted as any) share one section, headed with each name: one row per field, its
paths together as `EventDetail/(Send|Receive)/...`, and each rule's source named where they differ or only some
write it. Drop rules show as left untranslated. Events no rule of the mapping wrote are counted at the end.

Compact, the earlier layout: an **EventSource** table (one row per element, "(logon events only)" when only some
kinds of event have it), then an **Event types** table with one row per rule: Rule, TypeId and Description, Events,
and every other `EventDetail` element as `` `path` <- from = "sample value" ``. A CEF pipeline's section by event
type is a table of the keys every event gets, then one per kind of event (kinds with roughly the same keys
together, as rules are); compact, one table with an Event type column. An `AGENTS` doc's `## Documentation` section (`- field mapping: compact`) picks the layout; pass
`field_mapping_layout` (`by_event_type` or `compact`) only when the user asks for one, and it wins over the doc.

### Field descriptions

Each field's description says what it means for this source, for someone searching or reading the data: not the
schema's generic words, nor where it comes from (the table shows that). `write_documentation` asks for them: a
`needs_descriptions` reply lists the fields not yet described, each with where it comes from, its sample values and
`schemas_say`: what the vendor's documentation says of it (the source notes `record_source_notes` kept, matched by
the source field it is read from, or by the element the notes put that field in) and what the schemas say
(event-logging for where it comes from, ECS for an index field's name, ArcSight's dictionary for a CEF key). Infer each from its name, its path and its values, and the user's source notes
where they say, building on the schemas where they fit: a `subject` Data value under `Send` holding "Invoice 4411" is
"Subject line of the email sent"; a CEF custom slot (`cs1`, deviceCustomString1) is what this source puts in it, and
is described for each kind of event (`View: cs1`). Where the values don't make it clear, say what they look like and
that the meaning is unconfirmed. Until a field is described, the doc shows the first of those that says anything of it, the vendor's first. Call again with the
same arguments plus `field_descriptions={field: description}`, each field as the reply names it (and any ids the
reply gives). A Data value read from the same source under several elements is asked once, by its name
(`Data[@Name='Folder']`, with `under` listing the elements): one description covers it under all of them; where it
means something else under one, describe that one by its full path too. A row of event types shown together is
asked by the path the table shows (`EventDetail/(Authenticate|Process)/Action`). They are kept with the
documentation: an update asks only for fields new since, and a description given again replaces the kept one. The
reply says whether the doc was `created` or `updated` (`written`).

### What the section holds (indexing pipelines)

The index name, backend and time field; events left out (`drop_when`); and one row per index field (nested
fields by their dotted path, e.g. `user.name`): name, description, type, the event-logging path it comes from, how
often that path is populated in the sampled Events, and Sample values: the values the documents the pipeline wrote
from the sample got, up to three. By event type (the default) as for an events pipeline: a Common fields table (from
`EventTime`, `EventSource`, `TypeId`, `Description` and the ids), then a `####` section per action element the
fields come from (`EventDetail/Authenticate/...`), with its share of the sample's events, actions with roughly the
same fields together; compact, one table. An existing index's documentation is laid out the same way. A discovery pipeline lists the fields it maps explicitly, then every field the sample's
documents held, with how often and sample values. The agreed Elasticsearch index template is named too.

### An existing index

`write_documentation index_uuid=<the Elastic Index or Lucene Index doc>` documents an index that exists already
rather than a pipeline; the user confirms the index doc first. An index your build made is documented by its
indexing pipeline's doc (`pipeline_uuid=`), not with `index_uuid`: the call says so, unless the user asked for a doc
of the index doc itself as well (`index_itself=true`). The doc is named after the index doc and its Field mapping section is
generated from a survey through Stroom (`read_document` on the index doc shows the same survey): every field
Stroom has for the index, with a description, its type, its event-logging source path when a feeding pipeline
keeps an index plan, how often a sample of up to 100 documents (recent ones where there are any) held it, and sample
values. Write Purpose and
data yourself, from what you have seen of the source: what the source system is and what it records (the
feeds, their descriptions, the feeding and events pipelines and their docs), the kinds of events in the sample,
and who searches it; say what you do not know. The tool adds a "Data surveyed" summary under your text: the
documents and time span of the whole index, its source feeds and the pipelines that produced and index them. Give the user the reply's link;
`promote_build` puts the doc beside the index doc, or where the user chooses. Documenting an index again changes
the doc beside it (through a working copy, written back with its version control). A wide index is surveyed in groups
of columns; past 600 fields the rest are listed as not surveyed. Every field a feeding pipeline's plan writes must be
in the index (Stroom lists it for the index doc); if one isn't, the documentation is refused, naming it, rather than
written without it. Tell the user and ask them to reindex, or to check again in a minute (Stroom can be slow to list
a field only just indexed). Only if they want the doc now anyway (no event carries a value for it yet, say):
`document_missing_fields=true`, which lists it as not in the index. Leave out `stream_ids` and `accept_errors`: they
are for a pipeline's documentation.

## Errors: generated, with the ones the user accepted

`write_documentation` generates the Errors section from the Error streams processing the given streams produced:
each kind of error with its class (blocking, review, benign), element, severity, count and an example. Errors the
agent's own content caused are fixed before documenting, not listed as accepted. An error the agent could not
resolve (an inherited element, reference data, the source data) and the user says is benign is passed as
`accept_errors` (not Events written as `EventDetail/Unknown`: those are agreed per rule in `build_translation_xslt`,
`allow_unknown`, which is refused here) (element, an example as triage showed it, the user's reason, and optionally `matches`: the kind of
message it covers, with `*` for what varies, e.g. `No HR record for user svc-*`, matched anywhere in the message;
without it, the example's numbers and quoted values vary); the user confirms, and it is recorded in
the section, in a block the server reads. From then on triage reports that kind of error for the pipeline as benign,
with the user's reason, in stepping, Error stream summaries and evaluations, so it is not raised again. The block is
kept when the doc is rewritten, and travels with the doc when it is promoted.

## Who else reads it

The documentation is also how the feed is explained to the people who search it. `describe_feed` answers their
questions (what a feed holds, what a field means, how to search it) from the promoted docs, found by their
`mcp-generated` tag: Purpose and data for the overview, the Field mapping tables for a field. So write Purpose and
data for someone who never saw the build (the source system, what its records are, the kinds of event), and give
index fields descriptions that say what the value is, e.g. "The domain of the user's account" rather than
"user domain".
